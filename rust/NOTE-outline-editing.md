# アウトライン編集

## 結論

アウトライン編集は、画像貼り付けと切り分けて先に実装する。行／選択範囲とブロック、上下左右を一組として設計する。機能を「ブロックだけ」「左右だけ」に狭めない。

上下移動の保存方法は、2026-08-30に本家の通信を実測して確定した。本家と同じく、動かす行を削除し、新しい行IDで移動先へ挿入する。周囲の行は更新しない。

## 実装状況

- `522d7d7`で本家の送信差分を実測した。
- `6c024dc`でREADの行／選択範囲・ブロック・上下左右と、`Ctrl+G`の予備キーを実装した。
- 構造コミットの完了待ち、失敗・競合時の再読み込み、ページ移動中の古い応答、undo／redoの行ID追従までテスト済み。
- READの移動モード（`m`）を実装した。モード中は手元でだけ並べ替えて行IDを保ち、抜けるときに1コミットを送る。つかんだブロックの固定、位置が元へ戻ったときの無送信、失敗・競合時の巻き戻しまでテスト済み。
- EDITから同じ操作を使う対応は次のコミットで行う。未確定の入力を同じ構造コミットへ含め、操作後もEDITとキャレットを維持する。
- 兄弟がある向きでは、つかんだブロックは通常のブロック操作と同一に動く（全配置の総なめで検証）。1行ずつの経路は、字下げを戻して範囲がインデントと食い違っている間だけ有効にする。上の深い行はブロックの子ではなく前の兄弟の末尾なので、ここを取り違えると前の兄弟にブロックを割り込ませてしまう。
- 残っている弱点：`j` と `k` は厳密な逆操作にならない。1行ずつ外へ出たあとに `k` を押すと、そこにできた前の兄弟とかたまりごと入れ替わる。位置だけを見る規則では対称にできないと確認した。次のどちらかを選ぶ必要がある。
  - 直前と逆のキーを押したときだけ、その1手を取り消す（モードが自分の手順を覚える）。
  - モード中の `j`／`k` を兄弟単位ではなく1行単位の移動にする。常に対称で行き止まりもないが、大きな節を越えるのに打鍵数が増える。
- 残っている弱点：抜けるときのコミットが拒否されると、そのあとに始めた編集セッションが再読み込みで失われる。終了直前に拒否された場合も、伝える相手がもう画面を見ていない。単発のアウトライン操作と同じ問題なので、まとめて直す。

## 本家に合わせる操作

| 入力 | 対象 | 動作 |
|---|---|---|
| `Ctrl+↑` / `Ctrl+↓` | 現在行、または選択した連続行 | 直前／直後の行と入れ替える |
| `Ctrl+←` / `Ctrl+→` | 現在行、または選択した連続行 | 対象だけを1段浅く／深くする |
| `Alt+↑` / `Alt+↓` | 現在行を根とするブロック | 同じ親を持つ前／次の兄弟ブロックと入れ替える |
| `Alt+←` / `Alt+→` | 現在行を根とするブロック | 子孫を含めて1段浅く／深くする |

ブロックは、根の行と、それに続く「根より深い行」の最大連続範囲とする。表示上の折り返し行ではなく、ページのソース行を基準に判定する。

タイトル行は移動・インデントしない。選択中の `Alt` 操作は、対象が曖昧になるため受け付けない。`Ctrl` 操作は選択した連続行を1つの範囲として扱う。

コードブロックとテーブルを独自の保護領域にはしない。どちらもヘッダとインデントされた本文から成るため、ヘッダで `Alt` 操作をすれば全体が自然に動く。本文に対する `Ctrl` 操作は、通常の行操作として扱う。

## 編集セッションとの関係

アウトライン専用モードは作らない。READとEDITのどちらからも同じキーで操作できるようにする。

EDIT中に未確定の入力がある場合は、現在行を先に確定してから構造を操作する。操作後もEDITを保ち、カーソルを操作対象の論理行へ追従させる。IME変換中は構造操作を始めない。

`Tab` / `Shift+Tab` の既存動作は維持する。テーブル本文ではTabがセル区切りなので、アウトライン操作は修飾矢印を正本とする。

## 端末でキーが届かない場合

正本には、本家と同じ修飾矢印を使う。macOSや端末設定がキーを横取りする場合に備え、1打のプレフィックスから `h/j/k/l` を入力する予備経路も用意する。

既存の `Ctrl+O` はページ一覧と衝突するため使わない。`Alt+h/j/k/l` も、Escに続く文字入力との判別が曖昧になるため使わない。プレフィックスの第一候補は未使用の `Ctrl+G` とする。

```text
Ctrl+G h/j/k/l      行／選択範囲を左・下・上・右へ
Ctrl+G H/J/K/L      ブロックを左・下・上・右へ
```

プレフィックス入力中は、使えるキーをステータス行に表示する。Escまたは未対応キーで取り消し、後続キーを本文へ流さない。

## 保存方式の実測結果

検証ページは[アウトライン編集プロトコル実験](https://scrapbox.io/my-sandbox/アウトライン編集プロトコル実験)。ヘッドレスChromeから本家へキーを送り、同じページのWebSocket commitとREST APIの前後を記録した。

### `Ctrl+↑`は移動元だけを作り直す

`probe-root-b`を1行上へ動かすと、本家は次の2操作を送った。

```text
_delete 5c3247db85fcf2681a155c9c
_insert b10f1c6b36155ee30a72e94f  id=6a94522300000000006938c0 text="probe-root-b"
```

移動した行は新しい行IDになった。間をまたいだ行のID・本文・作成時刻・更新時刻は変わらなかった。リリースノートの「移動先の行の更新日時と行IDをupdateしない」はこの意味だった。

### `Alt+↓`はブロック全体を作り直す

子と孫を持つ3行のブロックを下へ動かすと、根・子・孫をそれぞれ`_delete`し、移動先の同じアンカーへ同じ順番で`_insert`した。3行とも新しいIDになり、入れ替わった兄弟ブロックのIDと時刻は変わらなかった。

### 左右移動は既存行を更新する

`Ctrl+→`は現在行だけに`_update`を送った。`Alt+→`は、根から「同じ深さ以下の行が現れる直前」までの各行へ`_update`を送った。すべての行IDと作成時刻を維持し、更新時刻だけが変わった。

以上から、現在の`page-edit-for-ai`で本家と同じ保存ができる。上下移動は移動元を`Delete`してから、移動先へ新しいIDで`Insert`する。左右移動は対象行を`Replace`する。sidは不要で、PATだけで全操作を保存できる。

「同じ表示結果になるから、行数の少ない側を動かす」という最適化はしない。本家も必ずユーザーが動かした側を作り直す。選んでいない行のID・履歴を変えないためです。

## 移動モード（決定済み）

READの実装後に、使ってみて出た課題が3つある。どれも同じ答え（常騐の移動モード）に行き着く。

### 課題1：READとEDITのどちらに置くか

操作の単位は行とブロックだから、行カーソルを持つREADが自然です。しかし並べ替えたくなるのは書いている最中だから、EDITからも使えなければ意味がない。

一方で、EDITでは印字キーがすべて入力なので、修飾キーなしの操作を置けない。この矛盾は、入っている間だけ印字キーを構造操作に使うモードを作れば解ける。

### 課題2：連続して動かせない、CtrlとAltを使えない人がいる

現在の `Ctrl+G` は1回限りなので、5行下げるには5回前置きを押す。さらに `Ctrl` 自体を使えない環境や利用者がいる。修飾キーを一度も押さない経路を、代替ではなく正本として用意する。

### 課題3：ブロックが箱書きの外へ出られない

これは本家と同じ振る舞いです。実測で確認した。最後の子で `Alt+↓` を押してもcommitは全く発生しない。本家のヘルプも、別のツリーの下へ移す方法を `alt+←` → `alt+↓` → `alt+→` と説明している。

つまり不足しているのは移動の規則ではなく、3手を連続で打てないことです。モードにすれば `h` `j` `l` の3打で済む。

### 提案するモード

READの印字キー1つで入り、`Esc` まで抜けない。中では修飾キーを使わない。

| キー | 動作 |
|---|---|
| `j` / `k` | ブロックを前後の兄弟と入れ替える |
| `h` / `l` | ブロック全体を1段浅く／深くする |
| `Esc` / `Enter` | モードを抜ける |

入口の候補は `m`。READでまだ使っておらず、意味も合う。既存の `Ctrl+G` と修飾矢印は別経路として残す。

EDITからは `Esc` で一度抜けて `m` と押す。修飾キーなし2打で届く。入った経路を覚えておき、抜けるときにEDITとキャレット位置を戻す。

### モードの最大の利点はコミットをまとめられること

今は1回の移動が1コミットで、完了を待ってから次を受け付ける。これでは連続移動が成立しない。また上下移動は行IDを作り直すので、5回動かすと5回IDが変わる。

モード中は手元だけで適用し、抜けるときに開始時点と最終位置の差分を、1コミットとして送る。行IDの作り直しも1回、undoも1手になる。位置が元に戻っていれば何も送らない。

モード中に他の人の編集が届いた場合は、編集中の行があるときと同じく保留し、抜けてから適用する。

### 見た目

動かしているブロックを選択範囲と同じ形で強調し、フッターにモードと使えるキーを出す。色だけで状態を表さない。

### 決めたこと

- 入口はREADの `m`。
- アウトライン編集は編集機能として扱う。修飾矢印はEDITのまま効くようにする。修飾キーを使えない場合の入口が `Esc` → `m` になる。
- モードを抜けるとき、動かしたブロックに編集中だった行が含まれる場合だけEDITへ戻す。
- 親がそこで終わっているだけのときは兄弟がないので、理由を出して止まる。ただし字下げを戻すと下の行が子に見えるので、その場合は `j` がその行を1行ずつ越える。リストの外へは `h` → `j` → `l` で出せる。
- コミットは抜けるときに1つだけ送る。位置と深さが元のままなら何も送らない。
- モード中は行IDを変えず、行の並びと字下げだけを手元で動かす。IDの作り直しは抜けるときの1回だけ。
- つかんだブロックは入った時点の行集合で固定する。字下げを変えても対象は増えない。
- 選択範囲があるときは `m` を受け付けない。`Alt` と `Ctrl+G` のブロック操作と同じ答えにする。黙って選択を捨てるより断る。
- つかんでいる間、矢印もブロックを動かす。ボタンを押していないマウス移動では抜けない。
- 画面の `VIEW` 表示は今回変えない。

### 先に直す前提（対応済み）

以前は構造操作の開始に `inflight == 0` を要求し、「次に返ってきた結果」で対応を見分けていた。これだと `Esc` が行をコミットした直後の `m` が弾かれる。

コミットジョブにIDを持たせ、結果と突き合わせるようにした。通常のコミットを送信中でも構造操作を始められる。順序は直列ワーカーが保つ。同時に扱う構造操作は1つだけで、その間ほかの変更を止める規則は変えていない。

## 実装の分け方

1. インデントから行・ブロック・兄弟範囲を求める純粋なプランナーを作る。
2. キー入力とカーソル／選択範囲の追従を実装する。
3. 左右移動を既存の`Replace`へ落とし込み、undo／redoまで通す。
4. 上下移動は、移動元の`Delete`と新しいIDを持つ`Insert`へ落とし込む。
5. READとEDIT、IME、WebSocket自己エコー、競合時再同期の回帰テストを追加する。

構造操作は1つのコミット、1つのundo単位とする。保存待ちの構造操作がある間にキーを連打した場合も、古い行順を前提に複数の操作を送らない。

## 受け入れ基準

- `Ctrl`は現在行または選択範囲だけを動かす。
- `Alt`は根と子孫をまとめて動かす。
- 上下移動は兄弟単位で、親・子を飛び越えない。
- タイトル行を変更しない。
- 折り返し幅や画面サイズで対象範囲が変わらない。
- 空行、全角空白、タブ、深さを飛ばしたインデントでも結果が一定である。
- 操作後もカーソルと選択範囲が対象行へ追従する。
- 1回の`u`で元へ戻り、`Ctrl+R`でやり直せる。
- 保存失敗や競合時に、画面だけ成功した状態を残さない。
- 左右移動では行IDを維持する。
- 上下移動では動かした行だけを新しいIDにし、周囲の行IDと時刻を維持する。
- 修飾矢印が届かない端末でも予備キーからすべて操作できる。
