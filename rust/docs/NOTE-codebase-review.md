## 認証・同期・文字列処理の不具合を修正した

| 優先度 | 修正前の問題 | 対応 |
| --- | --- | --- |
| P1 | `image_fetch.rs` が `/files/` や `scrapbox.io/` の部分一致で認証を付け、外部ホストにも PAT / SID を送り得た | リクエストを作る段階で HTTPS・ホスト・ポートを検証する。画像とファイル保存で同じ判定を使う |
| P1 | ページ URL や `file://` の `%日本語` をデコードすると、UTF-8 の途中をスライスして panic した | バイト単位でエスケープを読む `url::percent_decode` に統一する |
| P1 | WebSocket の複数行挿入で、既存 ID を飛ばしても挿入位置が進み、部分的な再送で範囲外アクセスが起きた | 実際に挿入したときだけ位置を進める |
| P1 | 通常の保存結果がページ移動後に届くと、移動先のタイトル変更や競合復旧を実行し得た | ジョブ ID ごとにプロジェクト・ページ ID・読み込み世代を記録し、保存結果の対象を照合する |
| P2 | 再同期で undo/redo を個別に検査し、新しい履歴が復元する行 ID を使う古い履歴まで捨てていた | アウトライン復旧と同じ `retain_replayable_history` を使い、実行順に検査する |
| P2 | 通常の `cargo test` が `COSENSE_SID` の有無で実サーバーへ接続した | 接続テストを明示実行にし、接続成功は表示文言に依存せず `SyncState::Live` で判定する |

保存結果の照合では、移動前の失敗を元ページの名前付きで通知する。
同じページへ戻った後に以前の保存が完了した場合は、現在のタイトルを直接変えず、再同期を要求する。
受信・保存・描画の結果は、それぞれが作られたページと世代に結び付ける必要がある。

URL のエンコードも API、リンク操作、Chrome、Web レンダラの4か所から `url.rs` に集約した。
コメントの読みやすい URL を作る `comment::encode_title_for_url` は、空白を `_` にする別の仕様なので維持した。

## 設計の良い点と残る課題

ライブラリと viewer の分離、行 ID に基づく編集、直列の保存ワーカーは、変更の影響を追いやすい構成になっている。
画像・Web 描画では、ページ世代やソースの世代による古い結果の破棄が既に使われていた。
表示幅、選択範囲、カーソル位置を画面バッファで検査するテストもあり、今回の分割の検証に使えた。

初回レビューで残した課題は2点あり、2026-09-07 の追補で次のように対応した。

| 残していた課題 | 対応 |
| --- | --- |
| `nav::load_page` や一覧取得が UI スレッドで同期通信し、API クライアントにタイムアウトがない | API・画像取得のクライアントに接続 10 秒、1 要求 30 秒の上限を設けた。Gyazo アップロードは同じ接続プールなので個別に 120 秒とした。リンク・一覧・履歴からのページ移動は `start_page_load` で背景スレッドに移し、結果に要求時の世代を付けて最新の要求だけを適用する。待つあいだは元のページや一覧を操作でき、状態行が読み込み先を示す |
| `editops::edit_script` が全ページの LCS 表を作る | 先頭と末尾で一致する行を表なしで合わせ、残る中央だけを LCS で比べる。中央の積が 400 万セルを超えるときは上から順に対にする。どの経路でも古い行はすべて消費され、新しい行はすべて生成される |

ページ移動の意図(履歴に積む場所、失敗時に戻す先、新規ページなら1行目を開く)は `PendingLoad` に記録し、到着時に実行する。
履歴の移動は要求時に移動先を取り出しているので、失敗したときと新しい要求に置き換わったときは元のスタックへ戻す。
取得スレッドはプロジェクト設定のキャッシュを温め、編集権限は結果(`LoadedPage`)に添えて返すので、初めて訪れるプロジェクトでも UI スレッドは通信しない。
テストでは取得スレッドを起こさず(`page_loads_on`)、結果をチャネルへ流し込んで到着時の処理を検査する。

背景処理化の追補レビュー(2026-09-07)で見つかった4件は、次のように対応した。

| 指摘 | 対応 |
| --- | --- |
| 読み込み待ち中に元のページで入力した内容が、到着時の `set_page` で消える | `arrive` が `set_page` の前に `session_commit_dirty` を呼び、汚れた行を保存キューへ入れる。保存結果はページと世代に結び付いているので、移動先へは当たらない |
| プロジェクト一覧やページ一覧へ移っても古いページ要求が有効なまま残り、到着すると一覧を置き換える | `open_projects` と `open_index_from` が一覧を置く直前に `abandon_pending_load` を呼ぶ。履歴ホップの目的地は元の山へ戻る |
| 「戻る」を素早く2回押すと、取り出した後にキャンセルした要求の目的地を末尾へ戻すため、履歴の順序が崩れる | `go_history` は取り出す前に待ちを片付ける。同じ向きの連打は途中の目的地に着いたものとして扱い、出発点と途中の目的地を反対側の山へ押す(A→B→C→D で `[` 2回なら B に着き、`]` は C、D の順)。向きが違う待ちは目的地を元の山へ返す |
| 権限取得が失敗するとキャッシュが残らず、到着時の `finish_load` → `can_edit_in` が UI スレッドで通信をやり直す | 取得スレッドが権限を調べて `PageLoadMsg` に添え、`finish_load` は引数で受け取る。同期経路(`load_page`)だけが呼び出し側で `can_edit_in` を使う |

再現テストは `tests/nav.rs` 末尾の3件(未保存入力の保護、一覧への移動による無効化、戻る連打の順序)。

まだ同期のまま残る通信は次のとおり。いずれも待ち時間はクライアントのタイムアウトで抑えられる。

- 起動時の最初のページ。画面に保つものがないので同期で問題ない。
- 編集後・競合後・ws 再同期後の `reload_page`。呼び出し元が結果を見てすぐに続きを実行する(自分のコミット ID の記録、競合時の入力の復元など)ため、続きを到着時処理へ移すには sync 側の設計変更が要る。
- 一覧・検索・プロジェクト一覧の取得(`open_index_from`、`search_index`、`open_projects`)。ページ移動と同じ仕組みで移せる。

TypeScript 版は初期スパイクで、公開時にリポジトリから除いた(履歴には残る)。
ブラウザ版には Rust と同じコメント形式を作る処理があるが、実行環境が別なので共通モジュール化はしていない。
ブラウザ版の DOM 操作とクリップボード操作の実機確認は今回の検証に含めていない。
