# REST API の429クールダウン

## 背景

Cosense の REST API は、ページ取得・一覧・画像など複数の要求を同じ制限の対象にする。
1本の要求が `429 Too Many Requests` になったあと、別のワーカーが待たずに要求を出すと、
同じ制限へさらに要求を重ねてしまう。個々の要求だけでリトライすると、この競合は防げない。

## 方針

`send_polite` と `send_edit_polite` の共有送信経路に、originごとのクールダウン期限を置く。
429を受けた要求は、`Retry-After`（秒）があればその値、無ければ既存の指数バックオフを期限として
保存する。期限は既存の期限より短くしない。次の要求は送信前に同じoriginの期限まで待つため、
ページ取得と画像取得のワーカーが同時に動いても、429直後の再送を分散できる。

無関係なホストまで止めないよう、キーは `scheme://host[:port]` とする。URLを構築できない
ストリーム要求は `*` にまとめる。クールダウンはプロセス内だけで、別プロセスの要求やサーバ側の
レート制限状態を推測するものではない。

既存の要求単位リトライは残す。429を受けた要求自身も共有期限を設定してから、期限を待って
再試行する。最終試行で429が返った場合も、後続の要求のために期限は残る。

## 運用上の境界

- クールダウンは429に対する送信抑制であり、429以外のエラーは変更しない。
- 待機はHTTPワーカー上で行い、TUIスレッドを直接止めない。
- サーバが返す `Retry-After` のHTTP-date形式は、従来どおり解釈できない場合の指数バックオフへ
  フォールバックする。
- 起動時の重複要求削減と、429を起動失敗にしない扱いは別の対策として続けて検討する。

## 実装

- `rust/src/api.rs`: `RATE_LIMIT_COOLDOWNS` と送信前待機を実装
- 既存の `retry_backoff` を共有期限の計算にも使用
